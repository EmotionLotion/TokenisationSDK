# Decisions

Durable design/process decisions for the programmable-rights harness. Append-only; each entry dated. (Build/consumer-fix decisions from the earlier loop live in `loop/decisions.md`.)

## D-0 (2026-06-24) — Harness model
The product-hardening harness lives in `harness/` and is **separate** from the earlier build/consumer fix-loop in `loop/`. The fix-loop's results (F1–F22) are inputs/evidence, not re-litigated here.

## D-1 (2026-06-24) — Foundation before modules
Solidify the generic foundation (tests, RBAC, errors, idempotency, audit) and **codify a module contract** before building any new vertical. Rationale: real estate and loyalty diverged in maturity; without a contract, each new module repeats bespoke effort and bakes in current gaps.

## D-2 (2026-06-24) — Critical path is enforced, not advisory
Order = `T0 → (T1,T2) → (T4,T5,T6) → T9 → future modules`, encoded in `task_graph.json` with dependency edges. Future modules (compute credits, dataset licenses, model/model-weight licenses, AI-agent access) carry `gate: blocked-until-foundation`.

## D-3 (2026-06-24) — Right-type taxonomy: decision deferred to T5 (recorded, not yet made)
Audit found loyalty's manifest references `MEMBERSHIP`, which is **not** in the core `RightType` enum (OWNERSHIP/ACCESS/BEHAVIOR/VERIFICATION). **Pending decision (T5):** either add `MEMBERSHIP` or map it to `ACCESS`; and design how future rights map on — proposed `USAGE`/`CONSUMPTION` (compute credits) and `LICENSE` (dataset/model), with AI-agent access modeled as delegated, scoped, revocable `ACCESS`. No change made yet.

## D-4 (2026-06-24) — Preserve strengths; do not rebuild
Do not re-architect the generic core or the ERC-3643 contract stack; do not rebuild the hash-chained audit/decision-receipt primitive or the pack/plugin registry. The module contract builds **on** these.

## D-5 (2026-06-24) — "Author once, enforce everywhere"
Target a single policy + metadata authoring model that projects to both off-chain (`PolicyEvaluator`) and on-chain (`IPolicyModule`/compliance modules). Unification work scheduled as T7 (policy) and T8 (metadata); design captured in `architecture_target.md`.

## D-6 (2026-06-24) — Verification discipline
Every task runs the five-phase loop (context → plan → action → verification → memory) and obeys the scope gate: no source change without an open task; one task per iteration; matching test/doc for every code change; no stack traces/secrets in API responses. Codified in `verification_rules.md`.

## D-7 (2026-06-24) — T0 made no code changes
T0 produced documentation/scaffold only. The first runnable code task is T1 (test the foundation).

## D-8 (2026-06-24) — Single permission matcher reconciles scopes ↔ role permissions (T2)
One canonical `permissionGranted(granted, required)` (`server/src/middleware/permission.ts`) is the sole authorization semantics, used by both the route guard (`requireScope`) and `iam.checkApiKeyScope`. Semantics: `*`/`admin` = superuser; exact; coarse action covers resource (`write` ⊇ `write:tokens`); `prefix:*` wildcard (`read:*` ⊇ `read`, `read:assets`); an action never implies another action (`write` ≠ `read`). Chosen over rewriting auth: smallest change, backward-compatible with coarse keys, and it makes the rich DEFAULT_ROLES permission strings enforceable. Full G3 closure needs T2a (issue keys from roles) + T2b (resource-level guards on all routers); tracked separately.

## D-9 (2026-06-24) — Programmable Right Module contract is the definition-of-done for verticals (T4)
Formalized in `programmable_right_module_contract.md`: every module (existing + future) is defined by a 17-section Module Spec (authored from `module_template.md`) and must pass `module_acceptance_checklist.md`. The contract extends the existing `PackManifest` rather than replacing it. Binding gates: (a) no future module is implemented before its Module Spec is complete and accepted; (b) a `pending-T5` right type blocks until T5; (c) redemption/consumption/revocation that cannot map onto the T6 primitive blocks until T6; (d) the four future modules stay deferred until T4+T5+T6 done and T9 (loyalty proof) passes; (e) existing modules are grandfathered but must reach conformance (real estate via T10, loyalty via T9). T4 deliberately does NOT finalize the right-type taxonomy (T5) or design the redemption primitive (T6) — it only fixes what a module must declare about each.

## D-10 (2026-06-24) — Right-type taxonomy ratified: two-level model (T5)
Canonical `RightType` (Level 1, small & stable) + module `RightProfile` (Level 2, attributes). Ratified canonical set: OWNERSHIP, ACCESS, BEHAVIOR, VERIFICATION (live) + USAGE (consumable/metered) and LICENSE (terms-bound/revocable) — ratified now, enum members added in T5a on the first consuming module (additive; no exhaustive switches → low risk). RightProfile attributes {transferable, divisible, expires, revocable, delegable, consumable} drive T6/T7, so T6 does not need the new enum values. MEMBERSHIP is resolved as an ACCESS profile, NOT a canonical RightType (closes D-3/RA-3); loyalty manifest changed to ['BEHAVIOR','ACCESS'] (metadata-only, non-breaking). Mapping: compute credits→USAGE, dataset/model licenses→LICENSE, AI-agent access→ACCESS(delegated profile), real estate→OWNERSHIP, loyalty points→BEHAVIOR. Full design in `right_type_taxonomy.md`.

## D-11 (2026-06-24) — Unified "Right Action" primitive (T6)
One server-persisted, audited, idempotent primitive (`redemption_consumption_primitive.md`) handles REDEEM | CONSUME | REVOKE | EXPIRE | VERIFY_ACCESS over any RightProfile, gated by T5 attributes (consumable/revocable/expires/divisible/delegable). It generalizes the existing securities redemption state machine (whose states become EXECUTING sub-states) and reuses the existing hash-chained audit, org-scoped idempotency middleware, and the T2 permission matcher rather than building new infra. Surface: `POST /api/v1/rights/actions` (+ history + receipt) and `client.rights.*`; existing /tokens/:id/redeem and /redemptions/* are kept as REDEEM specializations (back-compat). Implementation is broad → split into T6a (core service+table+conformance tests), T6b (server API+back-compat), T6c (SDK); first consumed by T9 (loyalty, retiring its in-memory redeem()), securities migrated under a T10 follow-up. T6 keys off RightProfile attributes, so it does NOT depend on T5a; policy gating (T7) and metadata validation (T8) are referenced as dependencies, not designed here. No bespoke/in-memory redemption is permitted in any module (module_acceptance_checklist updated).

## D-12 (2026-06-24) — Right Action core implementation choices (T6a)
Implemented the T6 primitive core as `server/src/services/right-action.service.ts` using the existing lazy `ensureTable()` + `rawQuery`/`execStatement` convention (DB-agnostic; no central drizzle-schema/migration change; auto-creates `right_actions` in the in-memory test DB). Service-level idempotency for mutating kinds via a UNIQUE(org_id, idempotency_key) index + replay-returns-existing; HTTP-level idempotency middleware still applies at the route layer (T6b). Status machine enforced via a transitions map (`isValidTransition`); `createAction` drives the validated happy path, mutating kinds emit a hash-chained audit entry (`right.<kind>.<status>`). The core deliberately does NOT own a balance ledger (module-owned, T9), policy gating (T7), or metadata validation (T8). Caveat captured: the `rawQuery` `$n`→`?` shim forbids reusing a placeholder number (use distinct $n + repeated params).

## D-13 (2026-06-24) — Loyalty integrates with the EXISTING server service, no parallel ledger (T9b)
T9a's audit missed the pre-existing server/src/services/loyalty.service.ts (loyalty_programs/accounts/transactions, account-balance model). T9b therefore INTEGRATES rather than replaces: appended redeemPoints/consumePoints/revokePoints wrappers that flow through RightActionService (audited, idempotent via findByIdempotencyKey) over the existing loyalty_accounts ledger. No new loyalty_balances table (avoids the fragmentation the harness prevents). The FIFO-batch model in the T9a spec is superseded by the existing account-balance model; EXPIRE maps to the existing expirePoints (wire later). Added findByIdempotencyKey to RightActionService so callers don't query right_actions directly. In-memory pack engine remains non-authoritative.

## D-15 (2026-06-25) — Loyalty operator dashboard is a native console page on the real SDK (T15, partial)
Delivered the T15 **loyalty operator dashboard** sub-goal: `ui/src/pages/LoyaltyConsole.tsx` in the `@tokenisation/console` app (route `/loyalty` + Platform nav), covering connect → setup (create program / open account / load-by-id) → overview cards → earn → redeem/consume/revoke → RightAction receipt → transaction-ledger evidence → developer snippet. **Key choices:** (a) it drives the **real** `client.loyalty.*` surface (no mock/fake data — honoring "real working flow"), built via `createApiClient` from `@tokenisation/sdk`; (b) the SDK is **lazy-imported only on connect**, so the page (and its test) don't eagerly pull the heavy umbrella — this also dodges the pre-existing `crypto-browserify` test-infra breakage (UI-INFRA-1); (c) the client factory is **injectable** (`makeClient` prop) so the page is unit-testable with a fake (`LoyaltyConsole.test.tsx`, 1/1, asserts the flow + required idempotency key).
